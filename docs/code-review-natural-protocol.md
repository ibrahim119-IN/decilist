# Historical JS review transfer protocol — 28 October 2026

Frozen product candidate: `a11174b2448f9228594b37e59100367f73c675a5`, specialist revision `047a67d224c6d90767dddea3712ee8af434eaff3`, three default rules, threshold 0.9. No model tuning or threshold change uses these cases. Corpus discovery and upstream fixes are visible to the evaluator, not to the stateless local review participant. No claim excludes historical public code from model pretraining.

Eight actual fix commits from four projects are pinned in `benchmarks/code_review_natural_catalog.json`. They were chosen before inference for different reproducible failure mechanisms and bounded JS source, without model-outcome selection. Historical parent code is used unchanged; no bug is injected. Identical evaluator-owned executable probes must fail on the parent and pass on the fix, with additional ordinary-behavior checks. Upstream source and licenses are retained outside the checkout. Adapted regression probes are identified as adaptations, not the full upstream suite.

Both broken and fixed versions enter evaluation. A fixed revision is a control for the repaired defect, not proof its entire file is bug-free. Report target-region persistent alerts separately from confirmed false alarms, other real defects, and unresolved alerts. Do not label every warning on a fixed file a false positive. The detached-method failure is a general behavioral control beyond the reviewer's three explicit checks. Closely related cases share projects/source; eight cases are not eight independent populations.

Static baseline: the pinned ESLint recommended profile on actual JS source, with Node/browser globals and no inline suppression. Record all diagnostics and parser/setup failures. This differs from the earlier TypeScript-only pilot; do not silently treat a parser failure as no warnings. Full upstream lint configurations and every analyzer are not claimed.

Paired ordinary/assisted local review: the same cached Qwen3-Coder-30B-A3B-Instruct Q4_K_M, stateless requests, temperature 0, identical generation budget, complete same source files and same lint diagnostics. The task is to review existing source and return a precise actionable finding and a minimal proposed repair, or no issue. Neither arm sees fix commits, commit descriptions, fixed source when reviewing broken code, private labels, protected probes or previous arm outputs. Assisted gets one live Decilist review of that source inside the measured clock; no-flags and failures remain in the assigned arm. Both arms may use identical bounded executable feedback when validating a repair. Human developer time is unmeasured.

Alternate arm order by case; fixed-control review order is reversed. Sequential trials avoid GPU/CPU workload contention; warmup excludes study cases. Record whole elapsed time including hint generation, output parsing, proposed edit application, and test verification. Keep failures/timeouts; never calculate a favorable success-only time median. A correct finding without a verified repair is reported separately and receives no repair-time-success credit. Proposal execution stays in disposable project copies, with source-only edits and unchanged protected tests/configuration. Three proposal attempts and a 180-second per-task cap are the upper bounds; no proposal is applied to Decilist or upstream repositories.

Before first case inference, freeze code/prompt/harness/corpus hashes and the actual runtime profile. Preserve source bytes and each request/response; parameter or harness changes after exposure are operational replays, not fresh trials. Fixture preparation failures before inference are retained with exclusion reasons, never silently replaced after seeing outcomes. Dates, licenses, source hashes and actual before/after probe results accompany the report.

Operational details fixed before inference: maximum 3072 generated tokens, seed 17843, prompt caching disabled, one run per assigned arm/version (32 trials). A no-issue reply ends the review; the evaluator does not reveal the hidden failure to force another guess. Broken revisions get up to three proposals with validation feedback after a proposed patch. Fixed controls get one proposal, with any regression check used only to detect damage, never to prove the claimed additional defect. Disposable-copy setup and original lint preparation are outside both clocks; live assistance, inference, edit application and validation are inside. This is source-file review with lint context, not a full repository agent or a reproduction of a human's usual tools.

Engineering gate for this small experiment: no lower verified-repair success than ordinary review, at least 20% lower capped median task time, at least half the pairs faster, and no increase in confirmed false alarms on corrected controls. Any unresolved control warnings prevent a clean false-positive claim. Passing is a bounded agent result only. Human time-saving claims need a separate randomized developer study with equal tasks, outcome verification, and actual consenting participants; neither the evaluator nor local model stands in for a measured human.

All downloads, environments, caches, model execution and scratch data stay on L. External source is inspected before execution; trusted open-source code and local tests run with OS permissions, not inside a claimed security sandbox. No external requests are made by the regression probes. Original sealed HTTPX transfer fixtures and prior trial records remain unused.
